# Phase 4〜6：執筆要件

共通文体はdocs/editorial-policy.md、保存・計測はdocs/note-format.mdに従う。

執筆担当はarticle-writer。Phase 4を親へ返してタイトル確定後、Phase 5〜6の文章を通して執筆する。
writerは割り当てられた本文だけを編集し、brief用の記録は親へ返す。画像agentの起動、画像の目視検品・本文への挿入、一括チェック、brief・manifest・stateの更新は親が担当する。
検証・独立監査で出た本文修正は親からwriterへ渡す。修正回数は記事全体で引き継ぎ、検証・監査の各3往復上限をリセットしない。

## Phase 4：タイトル・導入

- タイトルはPERSONAの場面・疑問と、読めば分かる答えや得られる判断材料を具体的に伝える。テーマ名に「整理」「設計」「基本手順」「徹底解説」を重ねて長くしない。これらの語自体は禁止せず、意味が重なる部分を削る。
- タイトル10案は、読者の場面・疑問・得られる答えの見せ方を変えて比較する。型は直球・理論反証・逆説・前提反転・因果反転から内容に合うものを記録するが、型の割合や採用制限は設けない。反転は本文の根拠で支えられる場合だけ使い、架空の通説や「〜より先に」を作って意外性を演出しない。
- 20〜45字程度を目安とし、自然な日本語と意味を優先する。字数合わせの語句追加はしない。テーマや対象が分かる語を前半に置き、KWは自然に使う。検索意図一致／具体性／読む理由の明確さ／本文回収可能性／非誇大を各5点で採点する。
- 各案に型と、約束した答えを回収する既存H2見出しを1つ記録する。上位3案の理由には、どの読者の疑問に応え、何が分かり、どの根拠で答えられるかを示す。高得点でも本文より広い約束や成果保証は採用しない。
- briefは `1. 候補タイトル｜型:直球｜5/5/5/5/5=25｜回収:H2見出し｜採用理由` の形式で記録する。タイトルで期待させた答えを本文で返し、別の答えへ誘導しない。
- メタは3案、各120〜140字。KWは先頭60字以内。「課題→解→読了後の状態」の順にする。
- メタはbriefだけに保存し、本文・frontmatterへ入れない。
- リードは最初の段落、導入はその後から目次まで。合計180〜320字程度を目安に、身近な場面または具体的な問い→答えの方向→読後に分かることを簡潔に示す。リードだけで伝われば導入の追加段落は不要。KWの冒頭位置や段落ごとの字数合わせより、自然な読み出しを優先する。
- 「〜について解説します」という定型紹介、対象読者の羅列、長い調査方法の説明で入口を埋めない。結論を隠して引っ張らず、理由・例外・使い方を本文で読む価値として残す。身近な場面は仮定例として描き、本人の体験に見せない。
- 導入の最終段落の後、最初のH2の直前に、noteの目次機能を表す`<toc>`を単独行で1回だけ置く。目次用の独自見出しや手書きリンク一覧で代用しない。
- 一次情報がないため権威・実績を創作せず、公開資料の調査・整理として信頼性を示す。

## Phase 5：本文

- plannerの全体配分で書く。目安は5,200字前後とし、上限まで修正余地を残す。
- リード・導入は合計180〜320字程度、まとめ・CTA等は約300字を目安に確保し、FAQは必要な問数だけ配分する。残りは本論の根拠・具体例・適用条件へ配分する。
- 各章は役割に応じて答え・理由・根拠のある具体例・例外・読者への適用を進める。全章を同じPREPの型で繰り返さず、前章で分かったことを次章の前提にする。短縮時も論拠や条件を落とさない。
- 具体例は条件と判断のつながりまで書く。たとえば転職なら「残業を減らしたい人」と「仕事内容を変えたい人」で求人の確認項目がどう違うかを示す。仮定例は明示し、数値・固有名詞を無理に足したり架空の成果を作ったりしない。公開資料の比較や条件別の説明で記事固有の価値を作る。
- アウトラインをそのまま説明文へ変換せず、各H2に「続きを読みたくなる入口」と「読者が腑に落ちる具体化」を置く。入口には問い・意外な事実・身近な場面・前章との対比、具体化には例・たとえ・簡単なケース・仕組みの可視化を使う。
- 事実の正確さを保ったまま、読者と一緒に考える語り口にする。「ここで気になるのは〜です」「たとえば〜」などは自然に使えるが、同じ呼びかけや接続句を機械的に反復しない。
- 専門用語を並べた段落、抽象名詞だけで進む段落、前置きだけで結論が遅れる段落は書き直す。難しい箇所ほど、短い言い換え→具体例→元の論点の順で説明する。
- 面白さのために事実を誇張しない。笑いを取りにいく文章より、「なるほど」「そういうことか」と小さな発見が続く文章を優先する。
- 1段落2〜4文を目安に、論点や話題の切り替わりで段落を分ける。見出しを含む各ブロックの間はMarkdown上で1行空け、長い段落を連続させない。
- H2・H3の前は公開時に空白段落が入る前提で構成する。見出し直後に余分な空白を重ねず、最初の本文を続ける。
- スニペットを狙う見出し直下に40〜60字の定義文を置く。
- H4はH3内の太字小見出しへ畳み込み、見出し階層を飛ばさない。
- 箇条書きだけで章を埋めず地の文で論理を運ぶ。全章続けて執筆し、章ごとの「続けて」は求めない。
- 初稿と監査反映後に一括チェックする。事実・文体・数値条件は親も読み直す。
- 初稿後は声に出して読むつもりで見直し、硬い定型句、同じ文型の連続、説明の重複、なくても意味が変わらない前置きを削る。各H2に読者の理解または興味を進める具体的な工夫があるか確認する。
- 各章の実測・配分差・要データ/要確認/要出典の残数を記録し、全章完了と総字数を報告する。

## Phase 6：FAQ・画像・リンク・CTA

- 本文で解消しない関連疑問があれば「よくある質問」に1〜3問を目安に置く。なければH2ごと省き、briefのFAQ数は0とする。回答は80〜120字程度を目安とし、正確に答えるのに必要な長さにする。本文の言い直しや問数合わせの周辺話題は足さない。FAQなしならFAQPageは生成しない。
- Article / HowTo / FAQPage / BreadcrumbListから適切なJSON-LDを実際に生成し、briefだけへ保存する。
- JSON-LDに本文にない事実を書かない。FAQPageなら質問・回答を本文と一致させる。
- 本文理解を助ける画像を各記事2〜3枚必ず実装する。装飾目的だけの画像や、同じ画像の再利用で枚数を満たさない。
- plannerの画像案から、複雑な仕組み・比較・手順・関係性など文章だけでは把握しにくい要点を優先する。記事の前半・中盤・後半へ偏りすぎないよう配置する。
- 各画像仕様に挿入位置、伝える要点、形式、構図、必要な短いラベル、避ける表現、alt、重複しないファイル名を記録する。altは画像の内容と役割を具体的に説明し、KWを詰め込まない。
- article-visual-generatorへ本文パスと2〜3件の仕様をまとめて渡す。確認済みの数値・固有名詞だけを使い、画像内で新しい事実や架空データを足さない。
- 返却画像をすべて目視し、本文との整合、文字の正確さ、可読性、構図、透かし・余計なロゴがないことを確認する。問題があれば対象画像だけを修正し、最終ファイルをdrafts/imagesへ保存する。
- 各画像を説明対象の段落直後へ `![alt](images/<slug>-body-01.png)` の形式で挿入する。リモートURL・data URL・空altは使わない。
- 必須アイキャッチは、記事タイトルとは別に、構図に合わせて読みやすく配置する短く引きのあるフックコピー（合計4〜12字目安、1〜2フレーズ）を作る。タイトルの転載・単なる短縮や説明文を避け、本文内容と矛盾しない独立した言葉にする。確定した記事タイトル・フックコピー・KICKER・雰囲気・出力先をbriefへ記録する。参考HTMLは画像agentが選ぶ。
- briefに全本文画像の生成結果、保存先、alt、挿入先、目視検品結果を記録する。必須アイキャッチも省略しない。
- plannerの内部リンクを自然な前後文とアンカーで本文へ反映する。候補がなければ無理に設置しない。
- GOALにつながる自然なCTAを中盤と末尾の2箇所へ置く。

## briefの必須記録

Phase 0の変数・質問/回答・仮定、Phase 1の全分析と出典、
Phase 2の3案採点・推奨理由・素材要否・クラスター・15語以上のエンティティ、
Phase 3の各見出しの役割・配分・狙い・画像案、Phase 4の10案の型/5軸採点/回収先/上位3理由/メタ3案、
Phase 5の実測、Phase 6の実装結果/画像指示/JSON-LD、
Phase 7の監査結果と反映箇所、未確定タグ、実行計測。
共通指示は複写せず、今回の分析・決定・証拠を保存する。
