# 8段階SEOライティングパイプライン（Phase 0〜7）

`note-article-seo-draft` が実行する各Phaseの詳細指示。SKILL.md の「note.com 向けの重要な調整」
を必ず先に読んでから、ここに書かれた各Phaseを実行すること。

とくに断りがない限り、各Phaseの出力はそのまま `<slug>.seo-brief.md`（内部設計資料。note には
投稿しない）に書き足していく。本文（`<slug>.md`）に反映するのは Phase 4 のタイトル/リード/導入文、
Phase 5 の本文、Phase 6 のFAQ・CTA文言のみ。

**担当**: Phase 1 は `seo-researcher` agent、Phase 2・3 は `seo-planner` agent、Phase 7 は
`seo-auditor` agent がそれぞれ独立に実行する（SKILL.md の「エージェント構成」参照）。
以下の各Phaseの指示は、委譲先のagentが従う仕様そのものでもある。Phase 0・4・5・6 は
`note-article-seo-draft` スキル自身（＝現在の対話セッション）が実行する。

---

## Phase 0：要件定義ヒアリング

**目的**: 制作に入る前に、共通変数（`{KW}` `{SUB_KW}` `{PERSONA}` `{GOAL}` `{MEDIA}` `{EEAT}`
`{SERP}` `{INTERNAL}` `{NG}` `{MIN_CHAR}` `{MAX_CHAR}`）を確定させる。

1. SKILL.md の「共通変数の決め方」表に従い、`AGENTS.md` / `articles/state.json` /
   引数から埋められる項目を先に埋める。
2. それでも埋まらない項目のうち、記事の成否への影響が大きい順に**最大7問**まで
   `AskUserQuestion` で質問する。各質問には回答例を1つ添える。
3. ユーザーが「不明」と答えた項目は、`{KW}` と `{MEDIA}` から妥当な仮説を立て、
   「仮定」と明示したうえで暫定値を置く。
4. 推測で変数を埋めて質問を省略しない。ただし、Auto Mode の方針上、
   `AGENTS.md`・`state.json`・`WebSearch` から合理的に取得・推定できる項目にまで
   質問を広げない（本当に他から取れないものだけを聞く）。

出力: 確定済み変数一覧 / 確認した質問と回答 / 仮置きした変数とその根拠。
最終報告に転記できる形で `<slug>.seo-brief.md` の冒頭に記録する。

## Phase 1：検索意図の逆算解析

**入力**: `{KW}` `{SUB_KW}` `{PERSONA}` `{SERP}`

**目的**: 検索結果で「良質」と判定されている条件を逆算し、記事が満たすべき要件を言語化する。

1. **意図の分類**
   - 主意図を Know / Do / Buy / Go から判定し、根拠を `{SERP}` の構成要素
     （広告の有無、リスト型記事の割合、公式サイトの順位など）で示す。
   - 主意図の下位に潜むマイクロインテントを4〜6個抽出する。
2. **上位記事の構造分析**
   - 検索結果一覧（スニペット等）から共通して登場する見出しトピックを列挙する。
   - 調査した信頼サイト（最大3件程度）が扱っている主要トピックを抽出する。
   - コンテンツ形式（リスト型／解説型／比較型／体験型）を判定する。
3. **欠落論点（コンテンツギャップ）の抽出**
   - どの記事も十分に答えていない疑問を5つ以上挙げる。
   - 各欠落論点について、読者が知りたい理由を1文で説明する。
4. **検索後の行動予測**
   - この記事を読み終えた読者が次に検索する語を3つ予測する。

**`{SERP}` の作り方（note.com向けの調整）**: ユーザーが `{SERP}` を貼り付けていない場合、
`WebSearch` で `{KW}` を検索する（原則1回の検索のみ）。検索結果一覧から大枠を把握し、
詳細の調査は**公式・公的機関・大手専門メディアなど信頼性の高いサイト最大3つ程度に絞って**迅速に行う。
多数のサイトを巡回したり、取得困難なサイトへの再試行・多重検索で時間を浪費しない。
検索結果から実際に確認できていない内容を上位記事の記述として捏造しない。調査しても
情報が不足する項目は「判定不能」と明記する。

**出力フォーマット**:
```
## 1. 検索意図
主意図：{分類}｜根拠：{根拠}
マイクロインテント：
- {内容}｜充足に必要な情報：{情報}

## 2. 上位記事の構造
共通トピック（頻出順）：
- {トピック}｜出現記事数：{数}
上位のみが扱うトピック：
- {トピック}
平均文字数：{数値} 字／主流形式：{形式}

## 3. コンテンツギャップ
- {欠落論点}｜読者が知りたい理由：{理由}

## 4. 次の検索語
- {キーワード}
```
（`<slug>.seo-brief.md` 用のため表は使わずリストで統一してよい）

## Phase 2：情報利得と勝ち筋の設計

**入力**: Phase 1 の出力 / `{EEAT}` / `{MEDIA}` / `{GOAL}` / `{INTERNAL}`

**目的**: 上位記事の「上位互換」ではなく、上位記事に存在しない価値（＝情報利得）を持つ記事の
設計図をつくる。

1. **差別化角度の立案**
   - Phase 1 のコンテンツギャップと `{EEAT}` を掛け合わせ、差別化角度の候補を3つ立案する。
   - 各候補を「独自性」「検索意図との整合」「実現可能性」の3軸で5点満点評価し、
     合計点が最も高い案を推奨する。
   - **`{EEAT}` に「一次情報なし」と記録されている場合、一次情報（実測データ・取材・体験）を
     前提にした案を推奨案にしない。** 既存知見の整理・構造化・比較など、捏造なしで成立する
     角度を優先する。
2. **一次情報の要求リスト**
   - 推奨案を成立させるためにユーザーが用意すべき素材を列挙する
     （実測データ／体験談／取材コメント／独自画像／検証結果）。
   - 各素材について「なくても成立するか」を Yes / No で示す。
3. **トピッククラスター設計**
   - `{MEDIA}` における本記事の位置づけを、ピラー記事かクラスター記事かで判定する。
   - `{INTERNAL}`（`articles/state.json` の `published` から自動収集した記事一覧）から
     発リンクすべき記事を最大3〜5本選び、アンカーテキスト案と設置章を指定する。
     候補が無い、または少ない場合は「内部リンク候補なし」と明記し、無理に選ばない。
   - 将来的に追加すべき関連記事のテーマを3つ提案する（`note-topic-ideas` の
     `topic_backlog` に追加する候補として使える）。
4. **エンティティ設計**
   - この記事が言及すべき固有名詞・専門用語・関連概念を15個以上列挙し、必須／推奨に分類する。

**制約**: `{EEAT}` に記載のない実績・経験をあるものとして扱わない。事実確認が必要な主張には
`[要出典]` を付記する。

## Phase 3：構成設計

**入力**: Phase 1・Phase 2 の出力 / `{KW}` / `{SUB_KW}` / `{MIN_CHAR}` / `{MAX_CHAR}`

**目的**: 執筆者（このスキル自身）が迷わず書ける粒度まで分解された、実装可能なアウトラインを作る。

1. H2を5〜7本設計する。各H2はPhase 1のマイクロインテントかコンテンツギャップのいずれかに
   1対1で対応させる。
2. 各H2にH3を2〜4本、必要に応じてH4を配置する。
   - **note.com向けの調整**: H4は本文化する際にH3の段落内の太字小見出しとして畳み込む前提で
     設計してよい（アウトライン上はH4のまま残し、Phase 5執筆時に畳み込む）。
3. 各見出しに以下のメタ情報を付与する。
   - 章の役割（結論提示／根拠提示／手順／反論処理／事例／比較）
   - 割り当て文字数（合計が `{MIN_CHAR}`〜`{MAX_CHAR}` に収まること）
   - その章に自然に配置するエンティティ
   - 狙うSERPフィーチャー（強調スニペット／PAA／画像／表 ※「表」はnote本文では箇条書きに
     置き換える前提で設計する）
   - 挿入する図表・画像の内容（実データが無い場合は概念図・スクリーンショット等、
     捏造データに依らない形にする）
4. 記事全体の論理展開が「読者の疑問→結論→根拠→適用→次の行動」の順になっているか検証し、
   崩れていれば章順を入れ替える。

**制約**:
- 見出し階層を飛ばさない（H2→H3→H4の順を厳守。ただし上記のとおりH4は本文化時に畳み込む）。
- 見出しに `{KW}` を機械的に詰め込まない。1記事のH2のうち `{KW}` を含めるのは2本までとし、
  残りは関連語・共起語で表現する。
- 体言止めの連続を避け、見出しだけを読んで内容が推測できる表現にする。
- 強調スニペットを狙う章は、見出し直下に40〜60字の定義文を置く設計にする。

## Phase 4：タイトル・メタ・導入部

**入力**: Phase 3の出力 / `{KW}` / `{PERSONA}` / `{SERP}`

**目的**: SERP上で上位記事と並んだときに選ばれるタイトルと、離脱を防ぐ導入部を作る。

1. **タイトル案を10本生成する**
   - 訴求軸を意図的に分散させる（数値提示／逆説／損失回避／権威提示／具体的成果／
     期間短縮／初心者向け宣言 など）。
   - 全角28〜32文字。`{KW}` は原則15文字以内に配置する。
2. **10本を採点し3本に絞る**
   - 評価軸：検索意図との一致（5）／`{SERP}` との差別化（5）／クリック誘因の強さ（5）／
     誇大表現でないか（5）。
   - 合計点の上位3本を選び、選んだ理由を各1文で述べる。
3. **メタディスクリプションを3本生成する**（**note.com向けの注**: noteには独自meta
   descriptionを設定する手段が無いため、これは `<slug>.seo-brief.md` の参考情報にとどめ、
   本文・frontmatterには反映しない）
   - 各120〜140文字。冒頭60文字以内に `{KW}`。
   - 「読者の課題→記事が提供する解→読了後の状態」の順で構成する。
4. **リード文（120〜160文字）** — 本文冒頭に使う
   - 冒頭20文字以内に `{KW}` を自然に含める。
   - `{PERSONA}` の状況をspecificに描写し、「自分ごと」と感じさせる。
5. **導入文（350〜450文字）** — 本文冒頭、リード文の後に続ける
   - 読者の疑問の代弁→結論の先出し→結論の根拠となる権威提示（`{EEAT}` を使用。
     「一次情報なし」の場合は誇張した権威提示をせず、調査・整理に基づく信頼性の示し方にする）→
     記事で得られること。
   - 結論を必ず先出しする。もったいぶらない。

**制約**: 「必ず」「絶対」「No.1」など根拠のない断定・最上級表現を使わない。`{NG}` に抵触する
表現を使わない。導入文で `{KW}` を2回を超えて使わない。

## Phase 5：本文執筆（章単位・自己チェック付き）

**入力**: Phase 3のアウトライン / Phase 4の導入部 / `{EEAT}` / `{NG}`

**目的**: アウトラインに割り当てられた文字数と役割を守りながら、最後まで読ませる本文を書く。

**note.com向けの調整**: 元パイプラインは章ごとにユーザーの「続けて」入力を待つ設計だが、
本スキルでは全H2章を通しで生成する。ただし章ごとの自己チェックは省略せず、
最終報告用に記録し続けること。

執筆ルール（各章に適用）:
1. 各章はPREP法（結論→理由→具体例→再結論）を基本とし、手順を説明する章のみ時系列順に
   切り替える。
2. 一文は60字以内を目安とし、同一文末表現を3回連続させない。
3. 漢字比率は30%前後を目安にする。
4. `{KW}` の出現密度は指標にしない。見出し・章の冒頭・まとめに自然に置き、それ以外では
   代名詞や関連語で言い換える。
5. 具体例には数値・固有名詞・条件を含める。`{EEAT}` に該当データが無い場合は数値を創作せず、
   `[要データ：{必要な数値の説明}]` と明記する。
6. 事実性が不確かな記述には `[要確認]` を付す。
7. 箇条書きは1章につき1箇所までとし、地の文で論理を運ぶ。
8. `{NG}` に抵触する表現を使わない。
9. Phase 3でH4として設計した項目は、対応するH3段落内で `**小見出し**` として書き出す
   （独立した見出しにしない）。

各章の生成後、以下を自己申告し記録する（最終報告にまとめて含める）:
- 実際の文字数と、アウトライン指定値との差分
- `[要データ]` `[要確認]` の残数

全章完了後、`- 全 {N} 章 完了（総文字数：{数値} 字）-` を自己申告に含める。

## Phase 6：実装要素の生成

**入力**: Phase 5で完成した本文全文 / `{INTERNAL}` / `{GOAL}`

1. **FAQの設計**
   - 本文が扱っていない周辺疑問を4〜6問抽出し、各80〜120字で回答する。
   - **note.com向けの調整**: 本文末に「よくある質問」などの見出し＋Q&Aとして本文に
     追記してよい（noteのMarkdown対応範囲内）。
2. **構造化データ（JSON-LD）の生成**（**note.com向けの注**: noteの記事に埋め込む手段が
   無いため `<slug>.seo-brief.md` の参考情報にとどめる。本文には反映しない）
   - 記事種別に応じてArticle / HowTo / FAQPage / BreadcrumbListを選択する。
   - 本文に存在しない情報をスキーマに書かない。
3. **画像の指示書**（実際の画像生成はこのスキルの範囲外。指示書のみ`<slug>.seo-brief.md`に残す）
   - 挿入位置ごとに、画像の内容・altテキスト（`{KW}` を機械的に入れず、画像の内容を
     説明する）・ファイル名案を出力する。
4. **内部リンクの配置**
   - Phase 2で決めたリンクを、本文中の自然な文脈に埋め込む形でアンカーテキストと
     前後の文を提示し、実際に本文へ `[アンカーテキスト](note_url)` として反映する。
5. **CTAの設計**
   - `{GOAL}` に接続するCTAを、記事中盤と末尾の2箇所分作成し、本文にも反映する。
   - 押し売りにならず、読者の次の行動として自然な文言にする。

## Phase 7：簡易ファクトチェックと修正

**役割**: 執筆者視点を離れ、第三者視点で事実関係の誤りやレギュレーション違反を簡易的にチェックする。

**入力**: Phase 5の本文全文（`articles/drafts/<slug>.md`） / `{NG}` / `{EEAT}` / （参考）Phase 1・3のアウトライン

**チェック項目**:
1. **数値・固有名詞・明白な事実誤認**: 本文中の主要な数値、固有名詞、年号などに明白な誤りや矛盾がないか（必要に応じ `WebSearch` 等で簡易確認）。
2. **`{EEAT}` の整合性**: `{EEAT}` にない実績・体験・データが、あたかも執筆者本人のものであるかのように捏造・断定されていないか。
3. **`{NG}` 抵触**: `{NG}` に挙げられた禁止表現・誇大表現に抵触していないか。
4. **タグの残存**: `[要データ]` `[要確認]` などの未確定タグが本文に残っていないか。

**手順**:
1. 対象ファイルを `Read` して簡易チェックを行う。点数付けや合否判定は行わない。
2. 指摘事項がなければそのまま完了とする。
3. 修正が必要な箇所が見つかった場合、該当箇所を引用し、具体的な修正後テキスト（修正前→修正後）を提示する。
4. 提示された修正案に従って、本文ファイル（`articles/drafts/<slug>.md`）の該当箇所を修正する。
   - 何度も差し戻して再監査ループを回す必要はない。指摘箇所を修正したらそのまま次のステップ（保存・投稿引き継ぎ）へ進む。
5. 人間が判断すべき事項（`[要データ]` `[要確認]` タグの残りなど）があれば一覧化する。

**出力フォーマット**:
```
## ファクトチェック結果
- 状況：{指摘事項なし / 修正指示あり}
- 総評：{簡潔なまとめ}

## 修正指示（修正が必要な場合のみ）
### 指示1：{修正の理由・内容}
修正前：{該当箇所の引用}
修正後：{書き直した文章}

## 人間の確認が必要な事項
- {項目（なければ「なし」）}
```

## 運用メモ

- 既存記事のリライトでは Phase 1→2→7 のみを回す（SKILL.mdの「軽量モード」参照）。
- `[要データ]` `[要確認]` タグが残ったまま「完了」として扱わない。この2つのタグが、
  このスキルが埋められない領域（実体験・実測データ・裏取り）と、ユーザーが埋めるべき
  領域との境界線になる。
