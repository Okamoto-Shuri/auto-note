# note-article-seo-draft

このリポジトリで記事の中身（何を・どう書くか）を生成する唯一のスキル。1本の記事に対して、
調査→戦略→設計→執筆→実装→ファクトチェックという制作工程をPhase 0〜7に分解して実行する。詳細な各Phaseの
指示は `references/pipeline.md` にあるので、実行前に必ず全文を読むこと。

**note.comへの実際の投稿・公開処理（API呼び出し）は `note-article-publish` の役割。** ただし
Phase 7の簡易ファクトチェック（および必要な修正）が完了した記事は、公開／下書きの指定が無ければ
本スキルの完了後にそのまま `note-article-publish` を通じて `is_publish: true` で本公開まで進める
（詳細は手順9）。

## エージェント構成（役割分担）

すべてのPhaseをこのスキル（＝現在の対話セッション）が自分でこなすのではなく、独立性・客観性・
コンテキストの汚染防止に意味がある工程だけを `.codex/agents/` の専任カスタムエージェントへ委譲する。
逆に、文体の一貫性が必要な工程（タイトル〜本文〜実装要素）は分割せず、このスキル自身が
通しで担当する。

| Phase | 担当 | 理由 |
|---|---|---|
| 0. 要件定義ヒアリング | このスキル自身 | ユーザーとの対話が必要であり、サブエージェントには委譲できない |
| 1. 検索意図の逆算解析 | `seo-researcher` agent | 検索時間は最小限に抑制し、信頼性の高いサイト最大3つ程度に絞って調査する。検索結果の生ノイズをメインの執筆文脈に持ち込まず、独立調査タスクとして執筆判断と切り離す |
| 2. 情報利得と勝ち筋の設計 / 3. 構成設計 | `seo-planner` agent | 差別化角度の比較検討・スコアリングは試行錯誤の分量が多いが、後工程が必要なのは確定したアウトラインだけ。ここを分離することでPhase4〜6の執筆文脈を汚さない |
| 4. タイトル・メタ・導入部 / 5. 本文執筆 / 6. 実装要素 | このスキル自身 | タイトルと導入と本文と実装要素（FAQ・内部リンク・CTA）は文体・トーン・文脈を共有する必要があり、分割すると継ぎ目が生じる |
| 7. 簡易ファクトチェック | `seo-auditor` agent | 書いた本人（＝このスキルの文脈）が自分の記事をチェックすると見落としが生じやすいため、執筆の経緯を共有しない独立した第三者に、完成品だけを見て客観的・簡易的にファクトチェックさせる |

Phase 1・2/3・7 をサブエージェントに委譲する際は、**1つのサブエージェントが完了して結果を確認してから
次を呼ぶ**（Phase1→2/3→…→7 の順で強い依存関係があり、本質的に並列化できないため、
複数を1メッセージでまとめて呼び出さない）。

## note-topic-ideas との関係

ネタ切れ防止のバックログ管理は引き続き `note-topic-ideas` が担当する。本スキルは
`{KW}` が引数で渡されなかった場合に `articles/state.json` の `topic_backlog` 先頭を使う
（「共通変数の決め方」参照）。

## note.com 向けの重要な調整（元パイプラインからの変更点）

このスキルが従う元の8段階パイプラインは、独自ドメインでの技術的SEO（JSON-LD埋め込み、
メタディスクリプション設定、H4見出し、比較表など）を前提にしている。note.comはこれらを
サポートしないため、以下のとおり調整する。

- **見出し階層**: note側の変換仕様に合わせ、実際の本文で
  使う見出しは `##`（H2相当）と `###`（H3相当）まで。Phase 3 でH4を設計した場合も、
  本文化する際はH4を独立見出しにせず、対応するH3の段落内に小見出し的な太字
  （`**〇〇**`）として畳み込む。
- **表（テーブル）**: noteの本文Markdownには変換されない。Phase 1・2・4・7などの
  比較表・スコアリング表は `<slug>.seo-brief.md`（設計・監査ドキュメント、note には
  投稿しない内部資料）にのみ使ってよい。実際の記事本文（`<slug>.md`）では表を使わず、
  箇条書きや地の文に変換する。
- **JSON-LD / メタディスクリプション**（Phase 6・4）: noteの記事ページに構造化データや
  meta descriptionを独自に埋め込む手段は無い。これらは「参考情報」として
  `<slug>.seo-brief.md` に残すのみとし、本文にもフロントマターにも書き込まない。
- **FAQ**（Phase 6）: 本文の末尾に「よくある質問」などの見出し＋Q&Aの形で本文に含めてよい
  （noteのMarkdown対応範囲内）。
- **画像・alt**（Phase 6）: 実際の画像ファイルの生成はこのスキルの範囲外だが、**アイキャッチ画像の生成およびnoteへの貼り付け（設定）はマスト（必須）**である。後続の `note-article-publish`（または `eyecatch-generator`）で必ずアイキャッチ画像が生成・適用されるよう、アイキャッチ用のタイトル・KICKER（ジャンルラベル等の短い文字列）・記事の雰囲気（速報／解説／入門／テック 等）を必ず `<slug>.seo-brief.md` に残す。参考テンプレートのファイル名は固定しない（生成側が雰囲気に合うHTMLを参考に、`image_gen` で画像を一から生成する）。本文中のその他画像指示書も同様に brief に残す。
- **Phase 5 の逐次確認**: 元パイプラインは章ごとに「続けて」の入力を待つ設計だが、
  本リポジトリの他スキルと同じく「1回の呼び出しで検証まで完結させる」方針に合わせ、
  全章をこのスキル内で通しで生成する。ただし各章ごとの自己申告（文字数差分・
  [要データ]/[要確認]の残数）は省略せず、最終報告にまとめて含める。

## 共通変数の決め方

元パイプラインの共通変数シート（`{KW}` `{SUB_KW}` `{PERSONA}` `{GOAL}` `{MEDIA}` `{EEAT}`
`{SERP}` `{INTERNAL}` `{NG}` `{MIN_CHAR}` `{MAX_CHAR}`）を、Phase 0 でゼロから聞くのではなく
先にこの順で埋め、**本当に他から取得できないものだけ**をユーザーに質問する。

| 変数 | 取得元（優先順） |
|---|---|
| `{KW}` | 呼び出し時の引数 → 無ければ `articles/state.json` の `topic_backlog` 先頭 → 無ければユーザーに確認 |
| `{SUB_KW}` | `{KW}` から自分で候補を立て、Phase 1 のSERP調査結果で裏付け・補正する |
| `{MEDIA}` | `AGENTS.md` の「記事のスタイルガイド」。未記載なら `articles/published/` の既存記事のトーンから推定し「仮定」と明記 |
| `{PERSONA}` | `AGENTS.md` のスタイルガイド。未記載なら `{KW}` と `{MEDIA}` から仮説を立てる（仮定と明記） |
| `{EEAT}` | `AGENTS.md` のスタイルガイドで固定方針が明記されている場合はそれに従う（現状: 一次情報を書かない方針のため、確認せず常に「一次情報なし」とする）。方針の記載が無い場合のみユーザーに確認する。実績・資格・一次情報は捏造できないため、無いなら「一次情報なし」として進める（Phase 2以降で一次情報前提の差別化案を選ばない） |
| `{GOAL}` | ユーザーに確認する（CV/回遊/指名検索など）。不明なら「note上での閲覧・スキ・フォロー獲得」を仮定と明記 |
| `{SERP}` | ユーザーが貼り付けていればそれを使う。無ければ `seo-researcher` agent に調査させる（Phase 1として委譲。このスキル自身はWeb検索しない） |
| `{INTERNAL}` | `articles/state.json` の `published`（`title` / `note_url`）を内部リンク候補として自動収集する |
| `{NG}` | `AGENTS.md` のスタイルガイド。未記載なら薬機法・景表法等の一般的な誇大表現NGのみを適用 |
| `{MIN_CHAR}` / `{MAX_CHAR}` | `AGENTS.md` のスタイルガイドで固定（現状: 4,000〜6,000字）。記載が無い場合のみ 4,000〜6,000字を既定にする |

Phase 0 でユーザーに質問して良いのは、上記の取得元をすべて試しても埋まらない項目
（典型的には `{GOAL}`。`{EEAT}` は `AGENTS.md` に固定方針があるため通常は確認不要）に限る。
1回のヒアリングで最大7問という元パイプラインの制約を守り、優先度の低い確認は後続Phaseに回す。

## 手順（フルパイプライン）

1. `references/pipeline.md` を読む。
2. 上記の表に従って共通変数を埋める。埋まらない項目があれば Phase 0 の指示に従い
   利用可能なユーザー入力手段で確認する（仮定を置いた場合は最終報告で明示する）。
3. **Phase 1** を `seo-researcher` agent に委譲する。サブエージェント起動ツールで
   `agent_type: "seo-researcher"` と `fork_turns: "none"` を指定し、依頼文に
   `{KW}` `{SUB_KW}` `{PERSONA}`
   （と、もしあれば `{SERP}`）を渡す。検索時間は最低限に抑え、信頼性の高いサイト最大3つ程度に絞って
   調査する指示を含める。返ってきたPhase1の分析結果を `<slug>.seo-brief.md` に記録する。
4. **Phase 2・3** を `seo-planner` agent に委譲する。`agent_type: "seo-planner"` と
   `fork_turns: "none"` を指定し、
   プロンプトに Phase 1 の出力・`{EEAT}` `{MEDIA}` `{GOAL}` `{INTERNAL}` `{KW}` `{SUB_KW}`
   `{MIN_CHAR}` `{MAX_CHAR}` を渡す。返ってきた差別化角度・クラスター設計・エンティティ・
   アウトラインを `<slug>.seo-brief.md` に記録する。以降のPhase 4〜6はこのアウトラインに従う。
5. **Phase 4〜6** はこのスキル自身が通しで実行する（分割しない）。
   - Phase 4: タイトル10本の生成・採点・3本選出、リード文・導入文を書く。
     メタディスクリプションは `<slug>.seo-brief.md` の参考情報にとどめる。
   - Phase 5: 「note.com 向けの重要な調整」に従い、全H2章を通しで執筆する。各章の
     自己申告（文字数・タグ残数）は記録しておき、最終報告にまとめる。
   - Phase 6: FAQは本文末に追記、内部リンク・CTA文言は本文に反映する。
     JSON-LD/メタディスクリプション/画像指示書は `<slug>.seo-brief.md` に記録する。
6. **Phase 7（簡易ファクトチェック）** を `seo-auditor` agent に委譲する。
   `agent_type: "seo-auditor"` と `fork_turns: "none"` を指定し、依頼文に対象記事の
   **ファイルパス**（チェックのため、この時点で一旦
   `articles/drafts/<slug>.md` に保存しておく）・`{NG}` `{EEAT}` を渡す。
   - 100点満点の採点や再監査ループは行わない。
   - `seo-auditor` から修正指示（修正前→修正後）が出た場合のみ、該当箇所を本文ファイル
     （`articles/drafts/<slug>.md`）に反映して修正する。
   - 指摘箇所の修正（または指摘なしの確認）が完了したら、そのまま次の手順へ進む。
7. ファクトチェックおよび必要な修正が完了したら、次の2ファイルが最新の状態で保存されていることを確認する。
   - `articles/drafts/<slug>.md`: 実際にnoteへ載せる記事本文。`note-article-publish`
     （`scripts/note_web_publish.js`）が解釈できる以下のfrontmatter形式・Markdown対応範囲を
     厳守する。
     - 対応: `#`/`##`（どちらも見出し扱い）、`###`、箇条書き `-`/`*`/`1.`、引用 `> `、
       コードブロック ` ``` `、画像 `![alt](path)`、太字 `**`、斜体 `*`、打消し `~~`、
       リンク `[text](url)`、目次 `<toc>`（単独行）、有料区切り `<pay>`（本文中に1回・
       行全体がこの文字列のみ）
     - 非対応・注意: テーブルは変換されない。`---` や `***` は水平線 `<hr>` に変換されるため、
       区切り目的以外で使わない（frontmatter 以外では `---` を書かない）。画像パスはリポジトリ
       ルートからの相対パス、または絶対パスにする。
     ```yaml
     ---
     title: "<採用したタイトル>"
     topic_id: "<topic_backlog の id、無ければ null>"
     status: "draft"
     created_at: "<ISO8601>"
     ---
     ```
   - `articles/drafts/<slug>.seo-brief.md`: Phase 0〜4・6・7の設計書・監査結果・
     残存する `[要データ]` `[要確認]` タグの一覧。note には投稿しない内部資料であることを
     冒頭に明記する。
8. `articles/state.json` を更新する。
   - `drafts` に `{ "file": "articles/drafts/<slug>.md", "title": ..., "kw": "<KW>", "created_at": ... }` を追加
   - トピックを `topic_backlog` から取り除き `topic_history` に移す（`kw` も記録する）
9. **投稿への引き継ぎ。** Phase 7 のファクトチェック（および必要箇所の修正）が完了した場合、続けて
   `note-article-publish` を呼び出す。公開／下書きの指定が無い場合の既定は本公開である。
   - `/loop`・`/schedule` などの無人実行中は、自動では呼び出さず、リポジトリ上の下書き保存で
     止めてその旨を報告する（`AGENTS.md` の安全設計を参照）。
   - ユーザーが依頼時に「下書きだけでいい」等、公開しない意思を明示していた場合も、
     note 上は下書き保存（`is_publish: false`）で止める。
   - 上記以外（指定の無い通常の呼び出し）では、`note-article-publish` に
     `articles/drafts/<slug>.md` を渡し、`is_publish: true` で本公開まで進める。
     改めてユーザーに「公開していいですか」と確認してはならない。
   - `note-article-publish` の結果（`articles/state.json` の `published` への移動、
     公開URLなど）を待ってから最終報告に含める。
10. 最終報告に必ず含める内容:
    - Phase 7 のファクトチェック結果（指摘有無、修正した箇所）
    - 仮定を置いた変数とその根拠
    - 残っている `[要データ]` `[要確認]` の一覧（0件なら「なし」と明記）
    - 保存した2ファイルのパス
    - 手順9で投稿まで行った場合はその結果（下書きURL／公開URL）、行わなかった場合はその理由

## 軽量モード（既存記事のリライト）

引数で「リライト」や既存ファイルパスが指定された場合は、元パイプラインの運用メモに従い
Phase 1 → 2 → 7 のみを実行する。

1. 対象記事のファイルパスを確認する（`articles/published/` または `articles/drafts/` 内）。
2. `seo-researcher` agent にPhase 1（検索意図分析）を委譲する。
3. `seo-planner` agentにPhase 2（情報利得設計）のみを依頼する（Phase 3の新規アウトライン設計は
   リライトでは不要なので省略してよいとプロンプトで明示する）。既存本文を「現状」として扱う。
4. `seo-auditor` agent に、対象記事のファイルパスを渡してPhase 7（簡易ファクトチェック）を依頼し、
   指摘結果と修正案（書き直し文つき）を受け取る。
5. このモードではファイルの上書き・保存は行わない。`seo-auditor` の修正案をそのまま
   ユーザーに提示し、反映を指示された場合のみ、対象ファイルを直接編集する。

## 停止条件・エスカレーション

- `{EEAT}` に無い実績・体験・データを創作しない。Phase 2 以降で一次情報前提の案を選ぶ場合、
  実在する `{EEAT}` の範囲でのみ成立させる。
- `{SERP}` は `seo-researcher` agent が実際に確認した内容のみを根拠にする。確認していない
  上位記事の見出し構成やデータを推測で断定しない（agentの「判定不能」をそのまま引き継ぐ）。
- `seo-auditor` agent から提示された修正案がある場合、その修正を本文に反映せずに公開へ進めない。
- `[要データ]` `[要確認]` タグが残ったまま「完了」として報告しない。残った場合は
  最終報告で一覧化し、公開前にユーザーが埋める必要があることを明示する。
- Phase 1〜7 のサブエージェント呼び出しは順序に強い依存があるため並列化しない。1つのサブエージェント
  呼び出しの結果を確認してから次を呼ぶ。
- note への実際の投稿処理（API呼び出し）自体は `note-article-publish` の役割であり、
  そちらの手順に従う。ただし手順9のとおり、Phase 7 のファクトチェック（および修正）が完了した記事は、
  指定が無ければ本公開まで含めて `note-article-publish` を続けて呼び出す（`/loop`・`/schedule`、
  および下書きのみの明示依頼を除く）。
- 1回のスキル呼び出しで作る（投稿する）のは記事1本まで。
