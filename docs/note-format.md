# note本文・検証形式

## 保存形式

本文はarticles/drafts/<slug>.md、設計資料は同名<slug>.seo-brief.mdへ作業中だけ保存する。
brief冒頭に「内部資料・noteには投稿しない」と明記する。

```yaml
---
title: "記事タイトル"
topic_id: null
status: "draft"
created_at: "実際の作成日時をISO8601で記録"
---
```

- 本文見出しは##と###。変換器は#もH2扱いだが、新規記事では使わない。
- Markdownでは見出し・段落などのブロック間を1行空ける。公開時はH2・H3の直前へ空白段落を自動挿入し、note上でも物理的な余白を残す。
- 対応：箇条書き、引用、コードブロック、太字、斜体、打消し、リンク、画像、単独行の<toc>と<pay>。
- `<toc>`は全記事で必須とし、リードと導入の後、最初のH2の直前へ単独行で1回だけ置く。冒頭、H2以降、複数箇所には置かない。
- H4はH3内の太字へ畳み込む。表、独自meta、JSON-LDを本文へ入れない。
- --- / ***は水平線になるため、frontmatter以外では区切りの意図がある場合だけ使う。
- 本文画像は記事ごとに異なる2〜3枚が必須。空altや同じ参照の重複は不可。
- 記事ファイル基準の相対パス（images/example.png）またはdrafts内の絶対パスを使う。リモート/data URLは不可。
- 画像は説明対象の近くへ単独行で置き、altに画像の内容と本文上の役割を簡潔に書く。本文にない主張・数値を画像だけで追加しない。
- MCPのdraft_path/eyecatch_pathはリポジトリルート基準。アイキャッチはdrafts/images内へ置く。
- 有料記事は<pay>を単独行で1回だけ配置し、MCPのpriceを指定する。
- state更新はMCP担当。frontmatterのdraftは入力形式であり、公開状態の正本はstateと取得結果。
- 作業開始時のmanifestへ、この作業で新規作成した本文・brief・本文画像・アイキャッチを登録する。全工程の完了後に登録済みファイルを削除し、stateのfileはnullにする。

## 統一計数

- Unicodeコードポイントで数える。frontmatter、リンク先URL、装飾・リスト記号、制御タグ、改行を除外する。
- 見出し文字列、リンク表示文字、画像キャプション、コード本文、文章中のスペースは含める。
- 本文総数はリード・導入・本論・FAQ・まとめ・CTAを含む。記事タイトルは別集計。
- 本文の最初の段落をリード、最初のH2までの残りを導入として集計する。
- FAQのH2は「よくある質問」、まとめは「まとめ」。FAQはH3ごとに1問とする。

## 一括チェックとbrief

`node scripts/check_article.mjs articles/drafts/<slug>.md` を実行し、stdoutのJSONをbriefへ転記する。
文字数・章差分・タグ・目次の有無と位置・本文画像の枚数/参照先・不整合をまとめて修正する。同名briefの機械読取欄は以下。

- 「### タイトル候補」内に `1. 候補タイトル｜型:理論反証｜5/5/5/5/5=25｜回収:H2見出し｜採用理由` を10行。型は理論反証・逆説・前提反転・因果反転・直球のいずれかを使う。
- 「### メタ候補」内に `- メタ文` を3行。得点等を同じ行へ書かない。
- 「### 章配分」内に `- H2見出しの文字列｜700` の形式で本論・FAQ・まとめを列挙する。
- `FAQ数: 4` のように独立行へ実際の問数を書く。
- JSON-LDはbriefのjsonコードブロックに保存する。
- 「## Phase 7：監査」の直下に「指摘事項なし」または全指摘を修正した事実として「反映済み」を記録する。
- 「## 実行計測」に各Phaseの開始/終了ISO時刻と呼び出し数を記録する。子内部の回数が不明なら不明とする。
