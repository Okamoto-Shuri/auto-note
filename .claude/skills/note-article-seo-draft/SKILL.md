# note-article-seo-draft

`note-article-draft` の上位互換スキル。1本の記事に対して、調査→戦略→設計→執筆→実装→監査という
制作工程をPhase 0〜7に分解して実行する。詳細な各Phaseの指示は `references/pipeline.md` に
あるので、実行前に必ず全文を読むこと。

**このスキルは記事の中身（何を・どう書くか）だけを担当する。** note.comへの投稿・公開は
`note-article-publish` の役割であり、ここでは一切行わない。

## エージェント構成（役割分担）

すべてのPhaseをこのスキル（＝現在の対話セッション）が自分でこなすのではなく、独立性・客観性・
コンテキストの汚染防止に意味がある工程だけを専任のサブエージェント（`Agent` ツール）に委譲する。
逆に、文体の一貫性が必要な工程（タイトル〜本文〜実装要素）は分割せず、このスキル自身が
通しで担当する。

| Phase | 担当 | 理由 |
|---|---|---|
| 0. 要件定義ヒアリング | このスキル自身 | `AskUserQuestion` でユーザーと対話する必要があり、subagentには委譲できない |
| 1. 検索意図の逆算解析 | `seo-researcher` agent | WebSearchの生ノイズをメインの執筆文脈に持ち込まない。実際に調べた事実だけを根拠にする独立調査タスクであり、執筆判断とは切り離すべき |
| 2. 情報利得と勝ち筋の設計 / 3. 構成設計 | `seo-planner` agent | 差別化角度の比較検討・スコアリングは試行錯誤の分量が多いが、後工程が必要なのは確定したアウトラインだけ。ここを分離することでPhase4〜6の執筆文脈を汚さない |
| 4. タイトル・メタ・導入部 / 5. 本文執筆 / 6. 実装要素 | このスキル自身 | タイトルと導入と本文と実装要素（FAQ・内部リンク・CTA）は文体・トーン・文脈を共有する必要があり、分割すると継ぎ目が生じる |
| 7. 品質監査 | `seo-auditor` agent | **書いた本人（＝このスキルの文脈）が自分の記事を採点すると、自分の判断を正当化する方向にバイアスがかかる。** 執筆の経緯を一切共有しない独立した第三者に、完成品だけを見て批判的に評価させることで、このバイアスを避ける |

Phase 1・2/3・7 を subagent に委譲する際は、**1つの `Agent` 呼び出しが完了して結果を確認してから
次を呼ぶ**（Phase1→2/3→…→7 の順で強い依存関係があり、本質的に並列化できないため、
複数を1メッセージでまとめて呼び出さない）。

## note-article-draft との違い・使い分け

- `note-article-draft`: お題から素早く1本書いて自己検証するだけの軽量スキル。ネタ切れ防止ループ向け。
- `note-article-seo-draft`（本スキル）: 検索意図の逆算・競合分析・差別化設計・タイトル比較・章単位の
  自己チェック・100点満点の品質監査まで行う重量スキル。狙ったキーワードでの上位表示や、
  読み応えのある1本に時間をかけたいときに使う。
- 両者は排他ではない。バックログ管理は引き続き `note-topic-ideas` を使い、生成方式だけを
  記事の重要度に応じて使い分ける。

## note.com 向けの重要な調整（元パイプラインからの変更点）

このスキルが従う元の8段階パイプラインは、独自ドメインでの技術的SEO（JSON-LD埋め込み、
メタディスクリプション設定、H4見出し、比較表など）を前提にしている。note.comはこれらを
サポートしないため、以下のとおり調整する。

- **見出し階層**: note側の変換仕様（`note-article-draft` と同じ）に合わせ、実際の本文で
  使う見出しは `##`（H2相当）と `###`（H3相当）まで。Phase 3 でH4を設計した場合も、
  本文化する際はH4を独立見出しにせず、対応するH3の段落内に小見出し的な太字
  （`**〇〇**`）として畳み込む。
- **表（テーブル）**: noteの本文Markdownには変換されない。Phase 1・2・4・7などの
  比較表・スコアリング表は `<slug>.seo-brief.md`（設計・監査ドキュメント、note には
  投稿しない内部資料）にのみ使ってよい。実際の記事本文（`<slug>.md`）では表を使わず、
  箇条書きや地の文に変換する。
- **JSON-LD / メタディスクリプション**（Phase 6・4）: noteの記事ページに構造化データや
  meta descriptionを独自に埋め込む手段は無い。これらは「参考情報」として
  `<slug>.seo-brief.md` に残すのみとし、本文にもフロントマターにも書き込まない。
- **FAQ**（Phase 6）: 本文の末尾に「よくある質問」などの見出し＋Q&Aの形で本文に含めてよい
  （note-article-draft と同じMarkdown対応範囲内）。
- **画像・alt**（Phase 6）: 実際の画像ファイルの生成はこのスキルの範囲外。指示書として
  `<slug>.seo-brief.md` に残し、必要なら `note-article-publish` のアイキャッチ作成手順
  （テンプレート方式）や、ユーザー自身の画像差し替えに委ねる。
- **Phase 5 の逐次確認**: 元パイプラインは章ごとに「続けて」の入力を待つ設計だが、
  本リポジトリの他スキルと同じく「1回の呼び出しで検証まで完結させる」方針に合わせ、
  全章をこのスキル内で通しで生成する。ただし各章ごとの自己申告（文字数差分・
  [要データ]/[要確認]の残数）は省略せず、最終報告にまとめて含める。

## 共通変数の決め方

元パイプラインの共通変数シート（`{KW}` `{SUB_KW}` `{PERSONA}` `{GOAL}` `{MEDIA}` `{EEAT}`
`{SERP}` `{INTERNAL}` `{NG}` `{MIN_CHAR}` `{MAX_CHAR}`）を、Phase 0 でゼロから聞くのではなく
先にこの順で埋め、**本当に他から取得できないものだけ**をユーザーに質問する。

| 変数 | 取得元（優先順） |
|---|---|
| `{KW}` | 呼び出し時の引数 → 無ければ `articles/state.json` の `topic_backlog` 先頭 → 無ければユーザーに確認 |
| `{SUB_KW}` | `{KW}` から自分で候補を立て、Phase 1 のSERP調査結果で裏付け・補正する |
| `{MEDIA}` | `CLAUDE.md` の「記事のスタイルガイド」。未記載なら `articles/published/` の既存記事のトーンから推定し「仮定」と明記 |
| `{PERSONA}` | `CLAUDE.md` のスタイルガイド。未記載なら `{KW}` と `{MEDIA}` から仮説を立てる（仮定と明記） |
| `{EEAT}` | **必ずユーザーに確認する。** 実績・資格・一次情報は捏造できないため、無いなら「一次情報なし」として進める（Phase 2以降で一次情報前提の差別化案を選ばない） |
| `{GOAL}` | ユーザーに確認する（CV/回遊/指名検索など）。不明なら「note上での閲覧・スキ・フォロー獲得」を仮定と明記 |
| `{SERP}` | ユーザーが貼り付けていればそれを使う。無ければ `seo-researcher` agent に調査させる（Phase 1として委譲。このスキル自身はWebSearchしない） |
| `{INTERNAL}` | `articles/state.json` の `published`（`title` / `note_url`）を内部リンク候補として自動収集する |
| `{NG}` | `CLAUDE.md` のスタイルガイド。未記載なら薬機法・景表法等の一般的な誇大表現NGのみを適用 |
| `{MIN_CHAR}` / `{MAX_CHAR}` | `CLAUDE.md` のスタイルガイド。未記載なら 2500〜4500字を既定にする（note-article-draft の1500〜3000字よりやや長め。SEO記事は網羅性を優先するため） |

Phase 0 で `AskUserQuestion` を使って良いのは、上記の取得元をすべて試しても埋まらない項目
（典型的には `{EEAT}` と `{GOAL}`）に限る。1回のヒアリングで最大7問という元パイプラインの
制約を守り、優先度の低い確認は後続Phaseに回す。

## 手順（フルパイプライン）

1. `references/pipeline.md` を読む。
2. 上記の表に従って共通変数を埋める。埋まらない項目があれば Phase 0 の指示に従い
   `AskUserQuestion` でユーザーに確認する（仮定を置いた場合は最終報告で明示する）。
3. **Phase 1** を `seo-researcher` agent に委譲する。`Agent` ツールで
   `subagent_type: "seo-researcher"` を指定し、プロンプトに `{KW}` `{SUB_KW}` `{PERSONA}`
   （と、もしあれば `{SERP}`）を渡す。返ってきたPhase1の分析結果を
   `<slug>.seo-brief.md` に記録する。
4. **Phase 2・3** を `seo-planner` agent に委譲する。`subagent_type: "seo-planner"` を指定し、
   プロンプトに Phase 1 の出力・`{EEAT}` `{MEDIA}` `{GOAL}` `{INTERNAL}` `{KW}` `{SUB_KW}`
   `{MIN_CHAR}` `{MAX_CHAR}` を渡す。返ってきた差別化角度・クラスター設計・エンティティ・
   アウトラインを `<slug>.seo-brief.md` に記録する。以降のPhase 4〜6はこのアウトラインに従う。
5. **Phase 4〜6** はこのスキル自身が通しで実行する（分割しない）。
   - Phase 4: タイトル10本の生成・採点・3本選出、リード文・導入文を書く。
     メタディスクリプションは `<slug>.seo-brief.md` の参考情報にとどめる。
   - Phase 5: 「note.com 向けの重要な調整」に従い、全H2章を通しで執筆する。各章の
     自己申告（文字数・タグ残数）は記録しておき、最終報告にまとめる。
   - Phase 6: FAQは本文末に追記、内部リンク・CTA文言は本文に反映する。
     JSON-LD/メタディスクリプション/画像指示書は `<slug>.seo-brief.md` に記録する。
6. **Phase 7（品質監査）** を `seo-auditor` agent に委譲する。`subagent_type: "seo-auditor"` を
   指定し、プロンプトに対象記事の**ファイルパス**（監査のため、この時点で一旦
   `articles/drafts/<slug>.md` に保存しておく）・Phase 1の出力・Phase 3のアウトライン・`{NG}`
   `{EEAT}` を渡す。
   - 90点未満、または「事実性・リスク」で3点以上の減点がある場合は改稿必須。
     返ってきた「修正前→修正後」に従って本文ファイルを実際に書き直す。
   - 書き直したら、**同じ `seo-auditor` agent を新規に呼び直す**（会話を継続させず、毎回
     フレッシュな独立評価にする。前回の採点結果を引き継がせない）。
   - 最大2回まで改稿・再監査を繰り返す。2回改稿しても基準を満たさない場合は、
     公開を勧めずスコアと理由をユーザーに報告して止める。
7. 検証を通過したら、次の2ファイルが最新の状態で保存されていることを確認する。
   - `articles/drafts/<slug>.md`: 実際にnoteへ載せる記事本文。`note-article-draft` と
     同じfrontmatter形式・同じMarkdown対応範囲を厳守する。
     ```yaml
     ---
     title: "<採用したタイトル>"
     topic_id: "<topic_backlog の id、無ければ null>"
     status: "draft"
     created_at: "<ISO8601>"
     ---
     ```
   - `articles/drafts/<slug>.seo-brief.md`: Phase 0〜4・6・7の設計書・監査結果・
     残存する `[要データ]` `[要確認]` タグの一覧。note には投稿しない内部資料であることを
     冒頭に明記する。
8. `articles/state.json` を更新する（`note-article-draft` と同じ扱い）。
   - `drafts` に `{ "file": "articles/drafts/<slug>.md", "title": ..., "kw": "<KW>", "created_at": ... }` を追加
   - トピックを `topic_backlog` から取り除き `topic_history` に移す（`kw` も記録する）
9. 最終報告に必ず含める内容:
   - Phase 7 の採点結果（観点別・合計点・判定）
   - 仮定を置いた変数とその根拠
   - 残っている `[要データ]` `[要確認]` の一覧（0件なら「なし」と明記）
   - 保存した2ファイルのパス

## 軽量モード（既存記事のリライト）

引数で「リライト」や既存ファイルパスが指定された場合は、元パイプラインの運用メモに従い
Phase 1 → 2 → 7 のみを実行する。

1. 対象記事のファイルパスを確認する（`articles/published/` または `articles/drafts/` 内）。
2. `seo-researcher` agent にPhase 1（検索意図分析）を委譲する。
3. `seo-planner` agentにPhase 2（情報利得設計）のみを依頼する（Phase 3の新規アウトライン設計は
   リライトでは不要なので省略してよいとプロンプトで明示する）。既存本文を「現状」として扱う。
4. `seo-auditor` agent に、対象記事のファイルパスとPhase 1・2の出力を渡してPhase 7
   （品質監査）を依頼し、採点結果と具体的な改稿箇所（書き直し文つき）を受け取る。
5. このモードではファイルの上書き・保存は行わない。`seo-auditor` の改稿案をそのまま
   ユーザーに提示し、反映を指示された場合のみ、対象ファイルを直接編集する。

## 停止条件・エスカレーション

- `{EEAT}` に無い実績・体験・データを創作しない。Phase 2 以降で一次情報前提の案を選ぶ場合、
  実在する `{EEAT}` の範囲でのみ成立させる。
- `{SERP}` は `seo-researcher` agent が実際に確認した内容のみを根拠にする。確認していない
  上位記事の見出し構成やデータを推測で断定しない（agentの「判定不能」をそのまま引き継ぐ）。
- `seo-auditor` agent の採点・改稿必須判定を、進行を優先させて自分の判断で緩めない
  （90点ルール／事実性3点減点ルールは agent 側の基準をそのまま採用する）。
- `[要データ]` `[要確認]` タグが残ったまま「完了」として報告しない。残った場合は
  最終報告で一覧化し、公開前にユーザーが埋める必要があることを明示する。
- Phase 7 の自動改稿は最大2回まで（＝ `seo-auditor` を最大3回呼ぶ: 初回監査＋改稿後の
  再監査2回）。それでも基準未達なら公開を勧めず状況を報告して止める。
- Phase 1〜7 の subagent 呼び出しは順序に強い依存があるため並列化しない。1つの `Agent`
  呼び出しの結果を確認してから次を呼ぶ。
- ここでは note への投稿・公開は一切行わない（`note-article-publish` の役割）。
- 1回のスキル呼び出しで作るのは記事1本まで。
